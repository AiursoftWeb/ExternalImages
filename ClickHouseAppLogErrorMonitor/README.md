# ClickHouse application log error monitor

A single-instance worker counts Error and Critical logs over the preceding 15 minutes every five minutes. Three, five and fifteen errors create or upgrade to sev4, sev3 and sev2; zero resolves, and severity is never downgraded. It discovers tables each cycle and skips unreadable or unsupported tables without resolving them. Supports the ClickhouseLoggerProvider schema (`LogLevel Int32`, .NET Error=4 and Critical=5) and numeric `String` levels used by older tables. Non-numeric string levels fail the query rather than being treated as zero. Evidence: the provider's [LogEntry](https://github.com/AiursoftWeb/ClickhouseSdk/blob/e9e97dedf6bc47873bf5546c5cc48012d4f86aec/src/Aiursoft.ClickhouseLoggerProvider/LogEntry.cs) declares `LogLevel` as `int`; the [SDK type mapping](https://github.com/AiursoftWeb/ClickhouseSdk/tree/e9e97dedf6bc47873bf5546c5cc48012d4f86aec) maps `int` to `Int32`; the [logger](https://github.com/AiursoftWeb/ClickhouseSdk/blob/e9e97dedf6bc47873bf5546c5cc48012d4f86aec/src/Aiursoft.ClickhouseLoggerProvider/ClickhouseLogger.cs) casts the Microsoft logging enum to `int`. Microsoft defines [Error=4 and Critical=5](https://learn.microsoft.com/en-us/dotnet/api/microsoft.extensions.logging.loglevel).

Incident creation includes a readable diagnostic summary and structured `Context`: `WindowStartUtc`, `WindowEndUtc`, `WindowBounds` (`[start, end)`), `ErrorCount`, `CriticalCount`, `TotalCount`, `TriggerThreshold`, `ThresholdLevel`, and the threshold rules. Both counts are aggregated in the same ClickHouse query. Severity-change and resolution reasons include the current window and counts; the creation snapshot remains unchanged during retries. No raw log messages or exception contents are forwarded.

Configure `NODE_NAME` (stable explicit node identity), `ALERTCENTER_URL`, `ALERTCENTER_API_KEY`, `CLICKHOUSE_URL` (default `http://clickhouse_clickhouse:8123`), `CLICKHOUSE_DATABASE` (default `AspNetCoreLogs`), `CLICKHOUSE_USER` (default `default`), `CLICKHOUSE_PASSWORD`, and `STATE_DIR` (default `/data`). Do not commit credentials. Use the dedicated AlertCenter application `clickhouse app log error monitor`, shared with Employees. Its key needs query, create, modify information, change severity and resolve permissions; it needs neither reopen nor mitigate.

Known table identities are persisted in SQLite, including identities recovered from pending creates and active incidents for this node/database. If a known table disappears from discovery, the cycle fails, reports the missing table, and does not refresh the health marker or resolve its incident. Other tables continue to be monitored; pending create receipts can still be reconciled without interpreting the missing table as zero. Coverage recovers when the table returns. Known tables are not automatically forgotten, even after an incident closes; deliberately retiring a table requires an explicit operator-managed state change while the monitor is stopped.

Persist `/data` on the same node across restarts. Run exactly one replica, use stop-first updates and never migrate it to an empty local volume. Pending creates are committed before sending; replacing or losing the volume compromises the guarantee during an ambiguous create. The state directory is bound to the node/database identity. Keep the AlertCenter key tied to the same application ID when rotating it; switching to a different application can orphan existing incidents and is not automatically detected or reconciled. Before deploying Stage 4 independently, provision only the monitor's bind directory, after its parent exists, using `install -d -o 1654 -g 1654 -m 0700 /path/to/clickhouse-app-log-error-monitor/data` (Proart: `/swarm-vol/ssd/clickhouse-app-log-error-monitor/data`; other nodes: `/swarm-vol/clickhouse-app-log-error-monitor/data`).

Local isolated integration on 2026-11-02 used the actual AlertCenter checkout with Local authentication, SQLite, no configured SMTP or push channels, the actual monitor image, and ClickHouse 26.10.3.7 from `pubhub.aiursoft.com/clickhouse/clickhouse-server@sha256:739e099abd1157390960a59e4532d21781d8fde57e6e4151cb920ea02c30b1ce` (amd64). The local AlertCenter UI created a disposable application and key with query, create, resolve, severity, and metadata scopes. Nine thresholds (0, 1, 2, 3, 4, 5, 14, 15, 16), mixed Error/Critical, lifecycle upgrades and resolution, manual closure, recurrence with a new ID, new tables, multiple tables/nodes, repeat scans, inaccessible tables and ClickHouse outage passed. A fault-injection proxy discarded one real create response; restarting the monitor with its original persistent Docker volume produced exactly one incident. The separate real ClickHouse test verified the inclusive lower and exclusive upper window boundaries and Warning exclusion. Three consecutive real normal-mode scans started approximately 300 seconds apart: at 06:32:44 UTC, 1 table in 0.148s; 06:37:46, 12 tables in 1.422s; and 06:42:45, 12 tables in 0.784s. All reported zero failures. The changing table count reflects tables added during integration; this is a small synthetic local workload, not a production performance benchmark. These are isolated tests, not production acceptance. No arm64 build was performed.

To reproduce the basic real-services setup, use a disposable ClickHouse container bound to loopback with a dedicated temporary user/password; build this directory's Dockerfile; and run AlertCenter from the checkout with `AppSettings__AuthProvider=Local`, `Storage__Path` set to a fresh temporary directory, `ConnectionStrings__DbType=Sqlite`, `ConnectionStrings__DefaultConnection=DataSource=/absolute/temporary/path/alertcenter.db;Cache=Shared`, and `ASPNETCORE_URLS=http://127.0.0.1:<free-port>`. Leave SMTP empty and create no push channels. In the local AlertCenter UI, create a disposable application and key with the five scopes above. Set `CH_TEST_URL`, `CH_TEST_USER`, and `CH_TEST_PASSWORD` and run `python3 -m unittest discover -s ClickHouseAppLogErrorMonitor/tests -p test_real_clickhouse.py -v` from the ExternalImages root. To exercise the container, create `AspNetCoreLogs` and logger-format tables on the disposable ClickHouse server, provide the local endpoints and scoped key to the monitor, and mount a writable persistent `/data` owned by UID/GID 1654. Use `--once` to run individual test scans, and normal mode for 300-second-cycle observation. Run only against isolated test services; never use production credentials. The ad hoc end-to-end lifecycle and response-loss scripts used for the run above are not included in the repository.

`python3 main.py --once` runs one scan; `--healthcheck` checks the last fully successful cycle. Logs report table counts, table and pending failures separately, and elapsed seconds without printing keys or log messages. Requests have 30-second HTTP timeouts and ClickHouse queries have a 20-second server execution limit. AlertCenter query paging requires stable, complete results; malformed or inconsistent results fail closed. Mutation errors are reconciled by re-reading and retrying at most three times; missing permissions or prolonged errors require operator intervention. The image uses `hub.aiursoft.com/aiursoft/internalimages/anduinos-internal:latest`, installs only Python and CA certificates, and runs as UID/GID 1654. The service uses only the Python standard library and has no third-party runtime dependencies. The integration results above were obtained before switching from the Python slim base to this internal base. Run focused tests from the ExternalImages root with `python3 -m unittest discover -s ClickHouseAppLogErrorMonitor/tests -v`. The optional real ClickHouse integration test requires an isolated disposable server and `CH_TEST_URL`, `CH_TEST_USER`, and `CH_TEST_PASSWORD`; it creates and drops a random test database. `tests/observe_mock.py` runs three local mock HTTP scans at the normal 300-second interval by default; `--interval` and `--cycles` allow shorter smoke tests. Mock timing is not production acceptance.
